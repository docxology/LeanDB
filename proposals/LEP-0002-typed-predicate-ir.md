# LEP-0002: Typed predicate IR

| Field | Value |
|---|---|
| Status | Draft |
| Number | LEP-0002 |
| Created | 2026-09-01 |
| Target | Post-0.2 |
| Primary goal | Pushdown soundness by construction; ground rule 3 |

## Summary

The select plan that `leandb_plan` reifies at each call site is currently
an untyped tree. `PushPred.cmp (table : Nat) (col : String) …` addresses a
column by position and name, ties neither to the tables in the `select`,
and does not relate the comparison value to the column's codec. Nothing
stops the tactic from emitting a plan over a column that does not exist or
a value of the wrong shape; the only guards are golden-plan tests and one
differential test.

This proposal replaces `PushPred` with an intrinsically typed
`Pred : List Type → Type`, indexed by the same table list that types the
predicate lambda, whose column references are Lean values generated by
`deriving LeanDb.Entity`:

```lean
-- t0."usdHr" becomes a term the compiler checks
Col.here Listing.Field.usdHr : Col [Listing] Price
```

With that comes a total denotation `Pred.denote : Pred ts → Rows ts → Bool`,
which makes two things stateable that today are only argued: that the
reified plan means the same as the lambda it was reified from, and that
the part sent to SQL never excludes a row the lambda would accept.

The design first appeared in the original design discussion
(`claude-discussion.md`, "§8.3 rebuilt around reify-then-plan") and shipped
in 0.2 as the untyped `PushPred` instead. This document lifts it into a
proposal, resolves one case the discussion did not anticipate (comparisons
through a validated newtype's representation), and fixes the scope: the
plan IR becomes typed; DDL, JSON, argv and diagnostics keep their strings.

## Why do this

`plan-v2.md` ground rule 3: *"No `name : String` fields for identity inside
the engine. Identity is a Lean declaration; the elaborator has `Name`s when
it needs them."* `PushPred` is the one place the engine breaks this rule
where it matters, and the consequences are concrete.

**The safety argument is half of one.** The engine's stated invariant is
that the lambda is always applied to fetched rows, so pushdown can narrow a
fetch but never change a result. That is true against *under*-narrowing. It
is false against *over*-narrowing: if the tactic ever emits a predicate
stricter than the lambda, the rows it excludes are gone before the lambda
runs. Today `PushPred.cmp 0 "usdHr" .le (toCol n)` typechecks whether or not
`"usdHr"` exists on table 0, and whether or not `n`'s encoding matches the
column's. A typed `Pred` makes the first unrepresentable and the second
checkable, and lets the no-over-narrowing property be proved once as a
theorem rather than re-tested per golden.

**Two deferred features need a plan that is data.** `plan.md` §4.4 wants the
query log to store *"the reified `Pred`/plan as data (not SQL text)"* so
that history is replayable; `_leandb_log` today stores the output of
`describe`, a string. §10.4 of the architecture wants the served wire to
carry a predicate rather than SQL, so injection is unrepresentable rather
than sanitized. Both need a canonical serialization that can be read back
soundly, which requires knowing which columns a table has — i.e. a
generated `Field` type with `ofName?`.

**The tactic's control flow is a function in disguise.** `PlanElab.lean`
splits into `strict` (exact translation or nothing) and `lenient` (per
conjunct, failures become `tt`). That split encodes a real soundness
argument — under `and` a dropped conjunct only widens, under `or` a dropped
disjunct would narrow — as tactic logic that cannot be stated or proved. With
opaque leaves in the IR it becomes a total function `Pred.approx` with a
four-line induction proof.

## Terminology

A **field symbol** is a constructor of the generated `α.Field` inductive,
one per declared field of entity `α`.

A **column reference** `Col ts τ` names a column of one of the tables in
`ts`, positionally, with its Lean type `τ`.

A **plan** `Pred ts` is a Boolean predicate over `Rows ts` as data. Its
**pushable projection** `approx p` is the same tree with every
non-translatable leaf weakened to `true`.

**Encoded domain**: the `LeanDb.Col` values that `ColCodec.toCol` produces —
what SQLite actually compares.

## Proposed design

### Field symbols, generated

`deriving LeanDb.Entity` additionally generates, for `structure Ticket`:

```lean
inductive Ticket.Field where
  | title | status | reporter | assignee | estimate | createdAt
  deriving DecidableEq, Repr

def Ticket.Field.ty     : Ticket.Field → Type        -- title ↦ Title, assignee ↦ Option (Ref User)
def Ticket.Field.get    : (f : Ticket.Field) → Ticket → f.ty
def Ticket.Field.name   : Ticket.Field → String      -- render-only: SQL, JSON, diagnostics
def Ticket.Field.ofName? : String → Option Ticket.Field
def Ticket.Field.all    : Array Ticket.Field
instance (f : Ticket.Field) : ColCodec f.ty          -- the field type's own instance, reachable from the symbol
```

Keyword field names follow the structure's own spelling (`«at»`,
`«open»`), exactly as closed-enum variants already do.

The `Entity` class exposes them:

```lean
class Entity (α : Type) where
  Field     : Type
  fieldTy   : Field → Type
  get       : (f : Field) → α → fieldTy f
  fieldName : Field → String
  codec     : (f : Field) → ColCodec (fieldTy f)
  fields    : Array Field
  tableName : String
  encode    : α → Array Col
  decode    : Array Col → Except DbError α
```

`Entity.columns` is no longer a stored field. It is computed:

```lean
def Entity.columns (α) [Entity α] : Array ColumnSpec :=
  (Entity.fields α).map fun f => columnSpec (Entity.fieldName f) (Entity.fieldTy f) …
```

This is the dependency direction the ground rule asks for: the string is
derived from the symbol, never the other way round. DDL, the JSON schema,
migrations and the fingerprint all continue to consume `ColumnSpec`
unchanged.

`Entity α` gains a `Type`-valued field and therefore lives in `Type 1`.
`Source`, `RowsOf` and the executor already quantify over `α : Type` and
are unaffected in practice; the cost is a universe annotation or two.

A structure that already declares a `Field` in its namespace is rejected
at derive time with a named error, the same way a field called `id` is
today.

### Column references

```lean
inductive Col : List Type → Type → Type 1 where
  /-- A declared field of the head table. -/
  | here  [Entity α] (f : Entity.Field α) : Col (α :: ts) (Entity.fieldTy f)
  /-- The head table's row identity (`Stored.id` / `.ref`). -/
  | id    [Entity α] : Col (α :: ts) (Id α)
  /-- Skip one table. -/
  | there : Col ts τ → Col (α :: ts) τ
  /-- View a column through a function that is its own encoding: for
      every `a`, `toCol a = toCol (f a)`. This is the typed form of the
      defeq guard that `colOf?` performs today, and the proof is `rfl`
      for any `ColCodec.via` newtype. -/
  | via   [ColCodec σ] (c : Col ts τ) (f : τ → σ)
          (h : ∀ a, ColCodec.toCol (self := Col.codec c) a = ColCodec.toCol (f a)) : Col ts σ

def Col.proj : Col ts τ → Rows ts → τ
def Col.codec : Col ts τ → ColCodec τ
```

Position is de Bruijn (`here`/`there`), so a reference to a table outside
`ts` is unrepresentable and `select [Ticket, User]` cannot receive a plan
that mentions `Comment`. `Rows [α]` is `Stored α` rather than
`Stored α × PUnit` (a deliberate ergonomic in `Select.lean`), so `Col.proj`
case-splits on the shape of `ts`; `RowsOf` already lives with the same
split.

`via` is the resolution to the case the original design did not cover. A
validated newtype `Price` with `ColCodec.via (·.milli) Price.make` is
stored as the encoding of `milli`. A predicate `l.val.usdHr.milli ≤ n`
compares in `Nat`, and SQLite compares `INTEGER`s; the two agree because
the column's bytes *are* `toCol milli`. `via` records that fact as a proof
the constructor demands, instead of a check the tactic performs. The same
constructor covers `some`: `Col.via c some (fun _ => rfl)` lifts
`Col ts σ` to `Col ts (Option σ)`, which is how `col == some col'`
becomes a column/column comparison.

### The plan

```lean
inductive Pred : List Type → Type 1 where
  | tt | ff
  /-- Column against a value, null-safe (`IS` / `IS NOT`). -/
  | eq    (c : Col ts τ) (op : EqOp) (v : τ)
  /-- Column against a value, ordered. Requires the type's ordering to be
      preserved by its encoding; NULL cannot occur because `Option` has no
      `SqlOrd`, so negation is exact. -/
  | ord   [SqlOrd τ] (c : Col ts τ) (op : OrdOp) (v : τ)
  | eq2   (a : Col ts τ) (op : EqOp) (b : Col ts τ)
  | ord2  [SqlOrd τ] (a : Col ts τ) (op : OrdOp) (b : Col ts τ)
  /-- Value against value; arises when a closed-world case split reduces
      a conjunct to a constant against a captured parameter. -/
  | vv    [ColCodec τ] [SqlOrd τ] (a : τ) (op : PushOp) (b : τ)
  | isNull (c : Col ts τ) | isNotNull (c : Col ts τ)
  | and (a b : Pred ts) | or (a b : Pred ts)
  /-- A conjunct the tactic could not translate. Runs in Lean, never in
      SQL. This is the residual, as a leaf. -/
  | opaque (f : Rows ts → Bool)
  /-- RESERVED, not in this proposal's scope (see LEP-0004): a quantifier
      over a child table related by a foreign key —
      `∃ row ∈ child, row.fk = this.id ∧ body`. Renders as `EXISTS (SELECT
      1 FROM child WHERE …)`; `∀` is `¬∃¬`. Listed here so the IR's shape
      is not closed before the restaurant base's central query (study
      §3.3) can be expressed as one `select`. -/
  | exists (child : Type) [Entity child] (fk : Col [child] (Ref α))
           (body : Pred (child :: ts)) : Pred ts
```

Three things are now structural that are tactic discipline today:

- an ordered comparison needs `SqlOrd τ` at the constructor, so the
  invariant "order comparisons never touch a nullable or closed-enum
  column" — which is what makes `PushPred.neg` exact — cannot be violated
  by a future tactic change;
- the comparison value is a `τ`, not a `LeanDb.Col`, so a value of the
  wrong encoding for its column is a type error;
- the residual is a leaf in the same tree rather than a count beside it.

### Denotation and the soundness theorem

```lean
def Pred.denote : Pred ts → Rows ts → Bool
  | .eq c op v,   r => EqOp.eval op (toCol (c.proj r)) (toCol v)        -- encoded domain
  | .ord c op v,  r => OrdOp.eval op (c.proj r) v                       -- Lean domain, via SqlOrd
  | .opaque f,    r => f r
  | …

/-- Weaken every opaque leaf to `true`, soundly: under `and` the leaf is
    dropped; a disjunction with an opaque side becomes `true` wholesale. -/
def Pred.approx : Pred ts → Pred ts

theorem Pred.approx_sound (p : Pred ts) (r : Rows ts) :
    p.denote r = true → p.approx.denote r = true
```

`approx_sound` is the no-over-narrowing property, proved once by induction
on `p`. It replaces the `strict`/`lenient` reasoning in `PlanElab.lean`,
which becomes: reify everything, wrapping anything unrecognized in
`.opaque` around its own sub-lambda, and let `approx` decide what ships.

`Pred.residuals` counts opaque leaves, which is what `log` reports today.

Equality is denoted in the encoded domain on purpose. `eq` renders as
`IS`, whose semantics on NULL is "both NULL" — that is a fact about
`LeanDb.Col`, not about `τ`, and the denotation should say so. Ordered
comparison is denoted in the Lean domain because `SqlOrd τ` asserts that
this agrees with SQLite; that assertion stays a documented marker with a
stated law (`OrdOp.eval op a b = OrdOp.eval op (toCol a) (toCol b)` under
SQLite's BINARY collation), tested by property, not proven. Proving it for
`String` would mean formalizing that UTF-8 byte order is code-point order,
which is true and not worth the engine's time.

### Rendering

```lean
/-- SQL for an opaque-free plan. Precondition, not a runtime check:
    callers pass `p.approx`. -/
def Pred.render (alias? : Bool) : Pred ts → String × Array LeanDb.Col
```

`render` reads `Entity.fieldName` at each `Col.here`, ignores `via`
(the underlying column already holds the encoding), and is otherwise the
existing renderer. `forTable`, `conjuncts`, `hasJoin` and `tables` port
unchanged in meaning. `neg` ports with `.opaque f ↦ .opaque (!f ·)`.

`render` is the remaining trust boundary: that the SQL it emits means what
`denote` says. That is what the differential test (`select` vs
`selectUnplanned`) continues to guard, now with a much smaller surface,
because everything above `render` is either typed or proved.

### The tactic

`leandb_plan` keeps its shape. `colOf?` returns a `Col ts τ` term instead
of `(Nat × String)`: `Stored.val c |>.field` becomes
`Col.there^i (Col.here α.Field.field)`, and the projection-through-codec
case becomes `Col.via c f (fun _ => rfl)` — the `isDefEq` the tactic
performs today is exactly what makes that `rfl` elaborate. Value builders
call `Pred.eq`/`Pred.ord` through `mkAppM`, so a value whose type does not
match the column fails to elaborate inside the tactic and the conjunct
falls back to `.opaque`, as any surprise does today. The case-split on
closed worlds is unchanged.

`PlanFor where'` remains the type that carries the lambda into the tactic's
goal; it becomes `def PlanFor (where' : Rows ts → Bool) : Type 1 := Pred ts`.

**Coherence.** With `denote` available, the property
`(reify where').denote r = where' r` is stateable. This proposal commits to
it as a property test in the engine suite over the fixture entities, and
to attempting `decide`/`rfl` on the existing golden plans as a
demonstration. It does not commit to discharging it by `rfl` at every call
site: `BEq` and `Decidable` instance reduction on user types will not
always compute, and a tactic that fails when a proof does not close is the
opposite of the "never fails" contract.

### Boundaries

Strings survive at every boundary, on purpose, and the boundary parses
into the symbol immediately:

| Boundary | Today | After |
|---|---|---|
| `rows --eq col=value` | `PushPred.cmp 0 col …` from the raw string — the value never meets the column's codec, so a canonical encoding (`K=4096,M=4096` vs `M=4096,K=4096`) is not honoured; found by `examples/kernels` | `Field.ofName? col` → parse through `Entity.codec f` → `Pred.eq (Col.here f) .eq v`; the boundary runs the smart constructor like every other one, and an unknown column is a typed error naming `Field.all` |
| `_leandb_log` detail | `describe` string | serialized opaque-free plan, plus `residuals` count (§4.4's "plan as data") |
| `serve` wire | argv strings only | unchanged in this proposal; the serialization exists for a later wire LEP |
| DDL, `schema` JSON, migrations, fingerprint | `ColumnSpec.name : String` | unchanged, now derived from `Field` |
| `DbError` fields | strings | unchanged — diagnostics, per `Core.lean`'s own comment |

### What is not in scope

- Changing `ColumnSpec`, `TableSpec`, `MigStep`, the JSON layer, the
  importer or the fingerprint. They consume derived strings and keep doing
  so.
- Typing `RefTarget`/`fkTable` (FK identity by table name). Same category.
- The served wire carrying `Pred`. This proposal produces the serialization
  and stops there.
- Implementing `exists`. It is reserved in the constructor list so `denote`,
  `approx` and `render` are written with it in view; its rendering, its
  denotation as a nested fetch in the reference semantics, and the tactic
  rule that recognizes `child.any`/`child.all` are LEP-0004.
- `SqlOrd` as a proof obligation.
- Cost-based planning over `Pred`. The discussion's "reify, then plan"
  becomes possible once `Pred` is data; nothing here plans.

## Staging

1. **Field symbols.** Extend the deriving handler; add `Field`, `fieldTy`,
   `get`, `fieldName`, `codec`, `fields` to `Entity`; compute `columns`.
   Pure addition — every existing test passes unchanged.
2. **`Col`, `Pred`, `denote`, `approx`, `approx_sound`, `render`.** New
   module beside `Plan.lean`; `PushPred` still drives execution.
3. **Tactic emits `Pred`.** Port `colOf?`, the builders, `caseSplit`; port
   every `checkPlan` golden in `Tests.lean` to the new constructors; add
   the coherence property test. Switch `Db.lean`'s two render sites and
   `Cli.rowsWhere`; delete `PushPred`.
4. **Log as data.** Serialize `approx p` into `_leandb_log.detail` as JSON;
   `log` renders it; `describe` survives as the human form.

Steps 1–2 can merge independently and carry no risk to bases. Step 3 is
the change; its verification is the existing suite plus every example
base's transcript reproducing the same SQL in `log`.

## Failure behavior

Unchanged in contract: the tactic never fails. A conjunct the new tactic
cannot type becomes `.opaque`, `approx` drops it, the fetch widens, the
lambda decides. What changes is that a *wrongly typed* plan is a
compile-time failure inside the tactic — and therefore a residual — rather
than a plan that reaches SQLite.

## Alternatives considered

### Keep `PushPred`, add a validation pass

A runtime check that every `(table, col)` exists in `RowsOf.specs` and
every value's `Col` matches the column's `sqlType` would catch the
existence and encoding errors. It would not give a `denote`, could not
state coherence, and would leave the `strict`/`lenient` soundness argument
in tactic control flow. It is strictly weaker for about a third of the
work.

### Projection functions as column identity

Carry `f : α → τ` in the tree and recover the SQL name from the
projection's declaration name at reify time. `denote` comes for free, but
two functions may share a name, a function may not be a column at all, and
the tree cannot be deserialized (a function is not data). The generated
`Field` enum is the same information with a finite, nameable, serializable
carrier.

### Field indices

`Fin (columns α).size` with a `fieldTy : Fin n → Type`. Equivalent in
power, worse in ergonomics: `Col.here ⟨2, by decide⟩` is not
`Col.here .usdHr`, and it does not read at the call site — which is the
ask.

### Full string removal

Chasing every `String` name out of `ColumnSpec`, `MigStep`, `DbError` and
the JSON layer. The project's own documents license those strings as
boundary and diagnostic data, and the migration diff must compare against
a schema stored as JSON in the instance. Nothing is gained, and the diff
against a stored snapshot becomes harder to reason about.

## Acceptance criteria

LEP-0002 is ready for implementation when the following hold in the engine
suite and in `examples/gpumarket`:

```lean
#check (Listing.Field.usdHr : Listing.Field)
#check (Col.here Listing.Field.usdHr : Col [Listing] Price)
#check (Col.via (Col.here Listing.Field.usdHr) (·.milli) (fun _ => rfl) : Col [Listing] Nat)

#check_failure (Col.here Listing.Field.usdHr : Col [Listing] Nat)       -- wrong type is unrepresentable
#check_failure (Col.here Model.Field.name : Col [Listing] ModelName)    -- wrong table is unrepresentable
#check_failure (Pred.ord (Col.here Listing.Field.usdHr) .le ⟨3000⟩ : Pred [Listing])
                                                                        -- no SqlOrd Price: must go through `via`
#check_failure (Pred.eq (Col.here Listing.Field.gpu) .eq (3 : Nat) : Pred [Listing])

theorem Pred.approx_sound : ∀ (p : Pred ts) r, p.denote r = true → p.approx.denote r = true
```

And:

1. Every existing golden in `Tests.lean` is ported and passes with the same
   rendered SQL.
2. `gpumarket log` reproduces byte-identical `pushed:` strings for every
   query in its transcript, including `under` after the projection fix.
3. The coherence property `(reify p).denote r = p r` holds over the
   fixture entities for every golden, by property test.
4. `Cli.rowsWhere` rejects an unknown column with a typed error that lists
   `Field.all`, and a closed-world value outside the vocabulary with the
   same error it raises today.
5. A plan serialized into `_leandb_log` round-trips through `Field.ofName?`
   to an equal `Pred` value.
6. `plan-v2.md` ground rule 3 has no remaining violation in
   `LeanDb/Plan*.lean`.
