## Why this document exists

The working belief driving this survey is that LeanDB — a typed database whose schema, queries, and migrations are Lean code, paired with agents that do the data entry and retrieval — should outperform existing systems on search-and-retrieval benchmarks, across domains. Before that belief can be tested, it needs to meet the actual landscape: what benchmarks exist, what each one actually measures, and whether any of them measure the thing LeanDB is built to guarantee.

"Search and retrieval benchmark" is not one tradition. It names at least four different measurement disciplines that grew up independently, use incompatible metrics, and answer different questions:

1. **Ranking quality over an unstructured corpus** — given a query and a fixed set of documents, did the system rank the relevant ones first? (classic IR, embeddings, vector indexes)
2. **End-to-end answer correctness for a generated response** — given a question, is the model's final answer right, faithful to its sources, and properly attributed? (RAG, knowledge-grounded QA)
3. **Structured-query correctness** — given a natural-language request over a database, does the generated query return the right rows, and does the system know when it can't answer? (text-to-SQL, table QA, database agents)
4. **Task success for an agent that acts** — given a multi-turn goal requiring tool calls against a live system, did the agent reach the correct end state while following policy? (agentic tool-use, web-browsing, database agents)

A fifth tradition, raw engine throughput (TPC-C/H/DS, YCSB), measures something different again — how fast a *known-correct* query executes — and says nothing about whether the query was the right one to ask.

None of these five traditions were designed with a typed, compiler-checked query layer in mind. That absence is itself the finding worth reporting, and it is what §7 below is about. Sections 1–6 are the survey proper: what exists, sourced, with unverified claims marked as such.

## 1. Classic information retrieval, semantic search, and vector-index performance

This is the oldest and most mature tradition. It treats the searched object as **unstructured text reduced to a vector**, and relevance as a scalar similarity between query and document vectors. Nothing in this cluster has a native concept of a typed field, a foreign key, or a hard constraint — filtering, where it exists, is bolted on as a secondary predicate over an otherwise opaque vector index.

**What this cluster structurally assumes.** The corpus is a bag of text with no enforced schema; ground truth is a per-query-document relevance judgment, not a query language over fields; the embedding function is scored purely on whether vector similarity reproduces that judgment. Filtering support, where benchmarked at all (VectorDBBench's and Big-ANN's "filtered" tracks), is a predicate layered on top of an otherwise opaque index, not a first-class part of the relevance measurement. Nothing here evaluates retrieval over typed, schema'd records — that is a different tradition (§3).

## 2. Retrieval-augmented generation and knowledge-grounded question answering

This cluster asks whether a system's *final answer* is correct, faithful to what it retrieved, and properly attributed — as opposed to whether the ranked list itself was good (§1). A recurring methodological split matters for reading every entry below: some benchmarks **separate** retrieval-quality metrics from generation/faithfulness metrics (so a low score tells you which pipeline stage failed); others report **one end-to-end number** that conflates the two.

| Benchmark | Org / year | Task | Scale | Metric | Notes |
|---|---|---|---|---|---|

| **TriviaQA / Natural Questions** (open-domain) | UW 2017; Google 2019 | Open-domain QA, now widely reused as retriever-evaluation corpora (DPR, REALM, RAG) | 96K / 307K examples | EM/F1, plus recall@k of the gold passage in retrieval papers | |

## 3. Structured data: text-to-SQL, table QA, database agents, and engine performance

This is the cluster architecturally closest to LeanDB, and the one containing the most direct evidence for §7's synthesis. Four sub-traditions, each answering a different question.

### 3.3 Hybrid structured-query + semantic reasoning: TAG-Bench

**TAG-Bench** (UC Berkeley Sky Computing Lab, 2024) names "Table-Augmented Generation" as a superset of text-to-SQL and RAG: NL questions that need SQL execution **plus** semantic/world-knowledge reasoning relational algebra can't express (subjective filters, semantic joins). Built on BIRD's databases with queries extended to require exactly that. Finding: pure text-to-SQL and pure RAG baselines both cap at ≤20% accuracy; a hand-engineered pipeline combining both reaches ~55%. This is direct evidence that neither structured-query execution nor retrieval alone suffices for composite queries — relevant to any system, LeanDB included, that claims to unify the two. [arXiv:2408.14717](https://arxiv.org/abs/2408.14717)

### 3.4 Database/data-agent benchmarks (multi-step, tool-using)

- **DA-Code** (academic, EMNLP 2024) — end-to-end agentic data-science workflows (Python/SQL/Bash) in a sandbox, graded by executing the agent's code and comparing outputs. 500 tasks; best baseline at publication ~30.5% accuracy. [arXiv:2410.07331](https://arxiv.org/abs/2410.07331)
- **DABStep** (Adyen + Hugging Face, 2025) — multi-step analysis over Adyen's real payments-company workloads, structured data plus supporting documents. 450+ real tasks; best reasoning agents around ~16% overall, ~14–15% on the hard tier. [huggingface.co/blog/dabstep](https://huggingface.co/blog/dabstep)

### 3.5 Reliability and abstention: the closest existing analog to LeanDB's thesis

This is the sub-cluster that matters most for §7. It directly tests whether a text-to-SQL system produces a confidently wrong answer versus knowing it can't answer — the exact failure mode LeanDB's typed refusal is built against.

- **TrustSQL** (KAIST, 2024) — explicitly benchmarks text-to-SQL **reliability**: correctly answer feasible questions *and* abstain on infeasible/unanswerable ones, built by re-annotating ATIS/Advising/EHRSQL with adversarial infeasible questions closely resembling feasible ones. Its **penalty-based Reliability Score** penalizes incorrect generation more heavily than correct abstention, and separately penalizes false abstention. Finding: very few systems achieve a positive reliability score across penalty settings — most text-to-SQL pipelines lack real abstention capability and default to guessing. [arXiv:2403.15879](https://arxiv.org/abs/2403.15879)
- **EHRSQL / EHRSQL-2024 shared task** — the same idea, earlier and domain-specific (electronic health records, MIMIC-IV), combining original unanswerable questions with TrustSQL's adversarial ones. [ACL 2024.clinicalnlp-1.62](https://aclanthology.org/2024.clinicalnlp-1.62.pdf)
- **NL2SQL-BUGs** (HKUST, KDD 2025) — a different angle: can an LLM judge detect that a syntactically valid, successfully *executing* SQL query is nonetheless semantically wrong (9 error categories, 31 subcategories)? 2,018 expert-annotated instances. Finding: SOTA LLMs detect only ~75.16% of semantically-wrong-but-executable SQL — current LLM judges themselves frequently miss confidently-wrong SQL. [dl.acm.org/doi/10.1145/3711896.3737427](https://dl.acm.org/doi/10.1145/3711896.3737427)

**The gap, stated precisely.** TrustSQL and EHRSQL-2024 reward a probabilistic abstention decision; NL2SQL-BUGs scores a post-hoc semantic-error judge. Neither frames the mechanism as a *type error* in the programming-language sense — a schema/type-checking failure caught before execution, as opposed to a classifier choosing not to answer, or a second model reviewing the first model's SQL after the fact. No benchmark surveyed here evaluates a system's ability to produce a genuine, compiler-enforced type failure as a first-class success outcome. That is a real, named gap in the published literature, not merely LeanDB's internal framing of one.

### 3.6 Raw engine performance — a different axis entirely

**TPC-C, TPC-H, TPC-DS** (Transaction Processing Performance Council) and **YCSB** (Yahoo, 2010) measure how fast and how concurrently a database engine executes **already-correct, fixed** transactions or queries — tpmC for OLTP throughput (TPC-C), QphH/QphDS for analytical query throughput over 22 or 99 standardized query templates (TPC-H/DS), operations/sec for key-value workload mixes (YCSB). None of the 22 TPC-H queries or 99 TPC-DS templates are natural-language-generated; they are pre-written and fixed. A system can top a TPC-H leaderboard while being unusable for natural-language querying, and vice versa. This is the axis LeanDB has not benchmarked at all and, per its own design docs (aggregates and pushed `SortBy`/`LIMIT` are still deferred engine work), is not yet positioned to compete on.

### 4.2 Web-browsing and deep-research agents

- **WebArena / VisualWebArena** (CMU, 2023–2024) — self-hosted realistic websites, functional/execution-based scoring against live state, not string match. 812 / 910 tasks. Best VLM agents at 16.4% vs. human 88.7% (VisualWebArena, original paper). [webarena.dev](https://webarena.dev/)
- **Mind2Web** (OSU, NeurIPS 2023) — 2,350 tasks over 137 real websites, 31 domains, with cross-task/website/domain generalization splits. [arXiv:2306.06070](https://arxiv.org/abs/2306.06070)
- **BrowseComp** (OpenAI, April 2025) — 1,266 adversarially "inverted" questions, hard to find but easy to verify. Adding browsing to GPT-4o raised accuracy from 0.6% to 1.9%; OpenAI's Deep Research agent reached 51.5% — evidence that orchestration, not tool access alone, drives this class of result. [openai.com/index/browsecomp](https://openai.com/index/browsecomp/)
- **DeepResearch Bench** (2025) — 100 PhD-level open-ended research tasks across 22 fields, scored on report quality and citation accuracy rather than a single short answer. [deepresearch-bench.github.io](https://deepresearch-bench.github.io/)

|---|---|

| Legal | **LegalBench** (162 tasks, issue-spotting/rule application), **LegalBench-RAG** (retrieval-only precision/recall over a 79M+ character legal corpus) |

| Code | **CodeSearchNet** (NL-to-code retrieval, ~1M pairs, 6 languages, MRR), consolidated since into **CodeXGLUE** and **CoIR** as broader multi-task suites |

### 4.4 Personal-assistant / memory-agent benchmarks: the closest analog to an ingestion loop

This is the newest cluster (2024–2026) and structurally the closest existing match to LeanDB's own framing of a data-entry loop paired with a query loop: an agent is fed structured facts over time and must later retrieve or reason over them faithfully, sometimes after a correction.

**LoCoMo** (2024, 50 long synthetic-but-refined conversations up to 35 sessions) and **LongMemEval** (2024–2026, 500 questions across single/multi-session recall, temporal reasoning, and a **knowledge-update** category — testing whether a system stays consistent after a fact is overwritten) are the two most cited. Newer, less-established entrants include **BEAM** (1M–10M token scale), **MemoryAgentBench** (scores retrieval, test-time learning, and forgetting as separate competencies), **PERMA** (event-driven preference tracking), **PrefEval/PersonaMem** (evolving user-preference tracking), and **OP-Bench** (scores *over*-personalization — spurious recall of irrelevant stored facts, directly relevant to a query loop that must return exactly the right record and nothing adjacent). As of this survey there is no single canonical benchmark in this space comparable to GAIA or BFCL; it is a fragmented, fast-moving cluster with several entrants self-reported by commercial memory-infrastructure vendors, so cross-system comparisons should be read cautiously.

### 4.5 E-commerce product search, in depth

Amazon ESCI (§4.3) is the largest and most cited e-commerce search-relevance set, but not the only one, and the two items brought to this survey directly — a Shopify dataset and a vendor's own comparison — turn out to sit on opposite sides of a distinction worth drawing precisely: a labeled product corpus is not automatically a search benchmark.

**The established benchmarks:**

**What the two linked items actually are.** The [Shopify product-catalogue dataset](https://huggingface.co/datasets/Shopify/product-catalogue) (48.3K products, Apache 2.0) ships product titles, descriptions, images, and ground-truth brand/category/secondhand labels — real, useful, human-verified data. But it has no queries and no query-product relevance judgments: it is a **product categorization/classification corpus**, the same genre as the Rakuten taxonomy challenge above, not a search-relevance benchmark like ESCI or WANDS. It could feed a search system (as category features, or as the product side of a query set someone builds against it) or serve as its own classification eval, but on its own it doesn't answer "given a query, did the right products rank first" — the question this whole section is about. Worth having on hand for a domain prototype's product data; not evidence for a search-quality claim.

**Onton's "Ontology 1" comparison** ([onton.com/research/ontology-1-benchmarks](https://onton.com/research/ontology-1-benchmarks)) is a genuine search-relevance comparison, not a labeling exercise, and it deserves a real read rather than a dismissal. What it reports: Onton's neurosymbolic product-search system, compared against Amazon Shopping and Google Shopping on 90 hand-written text queries plus 10 multimodal ones in the home-decor/furniture vertical, scored by three LLM judges (Claude Opus 4.8, Gemini 3.1 Pro, GPT-5.5) viewing screenshots of the top-10 ranked results from each engine, aggregated as mean Precision@10 with 10,000-resample bootstrap confidence intervals. Reported result: Onton 0.630 P@10 vs. Google 0.543 vs. Amazon 0.469, winning 52 of 90 queries outright.

That is more statistically literate than most vendor benchmarks — bootstrapped confidence intervals, three independent judges from three different labs, disclosed inter-rater reliability, a stated failure-case analysis, and published code/data. It is also, on its own numbers, not strong evidence for the general claim it is used to support, for four specific reasons the write-up itself half-discloses:

1. **The query set was authored by the same team evaluating against it, and shaped to the system's known strength.** Queries like "a chair that's comfortable for crying in" and "rug that hides cat puke but isn't beige" are aesthetic, negation-heavy, intent-laden — precisely the axis a neurosymbolic, LLM-mediated search architecture is built to win on. ESCI and WANDS source queries from real customer search logs; Onton's 90 queries have no claimed provenance beyond being written for this comparison. A benchmark whose author also selects which questions get asked is a different epistemic object than one built from logged real-world queries, independent of how careful the scoring afterward is.
2. **The reported reliability statistic undercuts the reported precision.** Krippendorff's α = 0.465 across the three LLM judges is below the threshold (≈0.667) content-analysis convention treats as a floor for drawing conclusions at all, and well below the ≈0.8 bar for high confidence. The write-up's own hedge — "the exact P@10 values are noisy and judge-dependent, but the directional finding is robust" — is doing real work to rescue a result whose measurement instrument it has just shown is unreliable; per-judge P@10 for Onton itself ranges from 0.528 (Gemini) to 0.759 (Opus), a wider spread than the gap being claimed against Google.
3. **The catalog-size confound is disclosed, not corrected for, and the correction that was applied cuts the wrong way.** Onton's indexed catalog is stated to be 100–1,000× smaller than Amazon's or Google's — meaning Onton is comparing a small, presumably pre-filtered slice against two general marketplaces — and 3 of the 93 queries were **excluded** from the average because Onton's catalog couldn't return 10 results at all. Dropping exactly the queries where the small-catalog disadvantage would show up hardest, rather than scoring them as a loss, biases the reported average in Onton's favor.
4. **Precision@10 with no recall is close to the metric most flattering to a small curated index.** The paper states recall is "unanswerable" without full competitor catalog access, which is true, but it also means the comparison only asks "of what Onton chose to show, how much looks relevant," never "how much of what exists did Onton fail to surface" — the exact question a 100–1,000× catalog disadvantage would hurt on.

None of this means the underlying architectural idea is wrong, and the write-up is meaningfully more transparent than the norm for this genre (disclosed limitations, published data, real statistics). But as evidence for "our search is better than Amazon's and Google's," a self-authored query set graded by LLMs with weak inter-rater agreement, on a catalog ~1,000× smaller than the systems it's compared against, with unfavorable cases excluded from the average, doesn't establish the general claim — it establishes that a small, curated index answers a query set built to its own strengths better than two general marketplaces do, which is a much narrower and less surprising finding.

**This pattern is not unique to Onton — it is close to the industry norm for search-API vendors right now (§4.6).**

### 4.6 AI-native web search index APIs (Exa, Parallel, Tavily, Brave, Firecrawl)

A newer product category sits adjacent to §4.2's web-browsing benchmarks: companies building search indexes and APIs specifically as the retrieval backend for LLM agents, rather than for human browsers. **Exa** (neural-embedding web search, tens of billions of pages indexed) and **Parallel** (Parallel Web Systems, raised a $100M Series A in early 2025, positions results with explicit provenance/evidence rather than ranked links) are the two most visible; **Tavily**, **Brave Search**, and **Firecrawl** compete in the same space.

Every one of them publishes its own benchmark comparison, graded by an LLM judge, against the others — and the results disagree in whoever's favor is publishing them. Exa's own evals report it leading FRAMES, Tip-of-Tongue, and Seal0, and beating Tavily 8.7 to 8.6 on an agent benchmark. Parallel's own comparison reports itself at 47% on Humanity's Last Exam against Exa's 24%, Tavily's 21%, and Perplexity's 30%, and 53% on BrowseComp against Tavily's 42% and Exa's 40% (April 2026). A third-party aggregator (AIMultiple, December 2025) puts Brave Search on top of the same rough comparison set, but notes the leading scores are "close enough that the differences could be random variation." This is the identical pattern documented in Onton's case above — self-run, LLM-judged, live-web (hence unreproducible and uncontrolled) comparisons where the publisher's own system wins its own test — playing out across an entire product category rather than one vendor.

The academic response to exactly this problem is worth citing as the more credible alternative: **BrowseComp-Plus** (Aug 2025, ACL 2026) rebuilds BrowseComp against a **fixed, curated, ~100K-document corpus** instead of the live web specifically so retriever quality can be isolated and results reproduced — its own numbers show why this matters, with accuracy ranging from 3.86% (BM25 + Search-R1) to 70.1% (GPT-5 + Qwen3-Embedding-8B) depending entirely on which retriever is paired with which model, a comparison no live-web vendor benchmark can hold still long enough to make. **Search Arena** takes the Chatbot-Arena approach instead — crowdsourced, blind, pairwise human preference between search-augmented LLM responses — trading a fixed corpus for removing the vendor from the grading loop entirely. Neither is a perfect substitute for the vendor numbers, but both exist because the vendor-benchmark pattern above is a recognized, named problem in the field, not a one-off complaint about one company.

*Adjacent case, not e-commerce:* [Applied Compute's turbopuffer case study](https://www.appliedcompute.com/case-studies/turbopuffer) (an RL-trained code-search agent, GRPO-fine-tuned Qwen 3.6-35B, evaluated with GPT-5 as an LLM judge against defined rubrics) is the same genre one domain over — a real, useful engineering result (hybrid BM25 + dense-embedding + reranking search cut ripgrep calls by 85–98% and scaled far better than brute-force grep as the corpus grew 15×) reported by the company whose product is the thing being credited with the improvement, graded by an LLM rather than humans. The finding is plausible and the scaling curve is a legitimate systems claim; it just carries the same "read the vendor's own eval as a vendor's own eval" caveat as everything else in this subsection.

## 5. Cross-cutting structural gaps

Reading all four clusters together, several things are consistently *absent*, independent of domain:

1. **Nothing scores "confidently wrong with exit code 0" as the primary, headline failure mode.** TrustSQL, EHRSQL-2024, and RGB's negative-rejection test come closest, but each treats abstention as a probabilistic decision by the generator or a post-hoc judge, not a compiler-enforced type failure. NL2SQL-BUGs shows this matters: LLM judges themselves miss ~25% of semantically wrong SQL that executes successfully.
2. **No benchmark treats a rejected/invalid ingestion event as a first-class scored outcome.** Every retrieval and RAG benchmark surveyed assumes the corpus is already-correct ground truth handed to the system; none scores whether a system *correctly refused* to admit a malformed or unsupported incoming record. This is a gap on the write side that mirrors the read-side gap in point 1.
3. **No benchmark spans schema evolution.** None of the text-to-SQL, RAG, or agentic benchmarks test what happens to previously-correct queries after the underlying schema changes — LongMemEval's "knowledge update" category is the closest analog, and it is about one fact changing, not a vocabulary or migration.
4. **Domain fragmentation is total.** Every vertical benchmark (finance, legal, biomedical, e-commerce, code) is its own island with its own metric; nothing scores one system across a dietary-constraint search, a hardware-compatibility search, and a financial-filing search with one comparable number. The field's own structure supports the idea that "one well-modeled domain at a time" (LeanDB's stated approach) is how the space is actually organized — but nothing measures breadth *across* domains as a single claim.
5. **Retrieval and structured execution are evaluated separately even where they clearly interact.** TAG-Bench is the one benchmark that puts this to the test directly, and its finding — pure text-to-SQL and pure RAG both cap near 20% on queries that need both — is the strongest existing evidence that a system unifying typed execution with semantic reasoning is solving a real, currently unscored problem.
6. **Engine throughput (TPC family) and correctness (Spider/BIRD family) are never combined.** A system's claim to be "fast and correct" has no single existing benchmark to be measured against; the two traditions don't share a leaderboard, a corpus, or a metric.
7. **Self-run, LLM-judged, vendor-vs-vendor comparisons are the norm, not the exception, in exactly the product category closest to LeanDB's own claims.** §4.5's Onton example and §4.6's web-search-API vendors (Exa, Parallel, Tavily, Brave) show the same shape every time: the publisher's own system wins its own test, graded by an LLM the publisher chose, against a query set the publisher wrote or a live corpus no one else can reproduce. This is not a defect specific to any one company — BrowseComp-Plus and Search Arena exist specifically because the field recognizes the pattern — but it is the exact failure mode a claim like "beats every benchmark" has to be careful not to repeat.

## 6. Notable internal precedent

This gap was independently anticipated inside this project before this survey was commissioned. `claude-discussion.md`'s design conversation sketches an unbuilt benchmark ("the Gauntlet") whose headline metric is **Silent-Wrong Rate (SWR)** — not error count, not speed, but the fraction of tasks a system completes while returning a confident, incorrect answer. Its proposed methodology: a plain-SQL agent arm needing zero LeanDB code (so its SWR can be measured before any LeanDB code exists), a LeanDB arm scored on the same tasks, paired evidence for every trap (a real `sqlite3` transcript producing a confident wrong answer next to the LeanDB snippet that refuses to elaborate, usable as both a negative test suite via `#guard_msgs` and a demo table), and an explicit, stated handicap (both arms get identical context and retries, acknowledging every model knows SQL far better than Lean from training data). `plan-v2.md` lists "the benchmark gauntlet" among deliberately deferred work, "revisit only after M5." Neither document contains a run, a score, or an implementation — this remains exactly what it was: a design, unbuilt.

That the internal instinct converges with what the published literature is missing (§5, point 1) is worth naming honestly for what it is: agreement between an internal design sketch and an external gap-analysis, not evidence of anything measured.

## 7. Where LeanDB's architecture would actually be measured

This section says, as precisely as the evidence supports, which of the above LeanDB could be run against today, which it would need new work to compete on, and which questions no existing benchmark can answer regardless of what LeanDB does. `WHITEPAPER.md` §9 already states plainly that the project "reports no new benchmark results or production reliability measurements" — nothing below changes that; it locates where such measurement would have to happen.

**§1 (classic IR/embeddings) is not a competition LeanDB is entered in, by design.** `WHITEPAPER.md` §3 already says this: "text search and embeddings can help resolve names, discover relevant sources, or retrieve candidates... any approximate candidate stage needs a coverage contract." LeanDB's typed predicate layer is a downstream consumer of a retrieval-stage candidate list, not a competitor to MTEB-ranked embedding models or Big-ANN-scale vector indexes. A claim of beating MTEB or VectorDBBench would be a claim about a component LeanDB does not build.

**§3.6 (TPC family) is a real gap, not a target LeanDB is close to.** The engine's own roadmap defers aggregates as a verb and pushed `SortBy`/`LIMIT` — exactly the machinery TPC-H/DS analytical queries need. Comparing LeanDB's engine throughput to TPC-H today would not be favorable, and nothing in the design claims otherwise.

**§3.1–3.5 (text-to-SQL family) is the closest existing external analog to LeanDB's query loop, and the most immediately actionable place to measure it.** Spider and BIRD score execution accuracy against one correct SQL string — rewarding a plausible query that happens to match, which is precisely the metric TAG-Bench and NL2SQL-BUGs show is insufficient. TrustSQL's penalty-based Reliability Score is the closest published methodology to what SWR would need, and it is directly reusable: TrustSQL's own finding that "very few systems achieve a positive reliability score" means the bar an adapted LeanDB arm would need to clear is empirically low, not a strawman. No published benchmark, including TrustSQL, tests a *type-checking* failure as the abstention mechanism — every one of them scores a probabilistic decision or a second-model judgment. That is a genuine, citable gap (§3.5), and it is the one place this survey found where LeanDB's actual mechanism (a query that does not elaborate) has no existing external measurement to be compared against, favorably or otherwise.

**τ-bench (§4.1) is architecturally the nearest published benchmark shape to LeanDB's hosting surface.** Its three-part success condition — user intent satisfied, database state correct by direct diff, policy compliance — maps almost directly onto what `serve --http`, the MCP tool surface, and a base's registered queries already expose. Its `pass^k` metric (all k trials must succeed) is a stronger and more relevant reliability bar than a single pass@1 number, and matches the byte-identical-replay discipline this project already holds itself to for plan changes. Building a τ-bench-style task suite against an existing base (tickets or eats) would require no new LeanDB infrastructure — only new task definitions and a scoring harness — because the serving surface it would exercise is already built and tested.

**§4.4 (memory-agent benchmarks) is the closest analog to the ingestion loop specifically, and the newest, least-settled cluster surveyed.** LongMemEval's knowledge-update category and OP-Bench's over-personalization scoring are the nearest existing tests of "does a system correctly handle a correction to previously-stored structured facts" and "does retrieval return exactly the right record, not adjacent noise" — both central to `WHITEPAPER.md` §4's evidence/freshness/uncertainty design, and both currently untested against any LeanDB base.

**§4.3 (vertical benchmarks) supports the "in all domains" framing structurally, but does not let anyone claim it yet.** The field's own organization — one benchmark per domain, no shared metric — matches LeanDB's bet that generality comes from many well-modeled domains rather than one universal schema (`WHITEPAPER.md` §1). But no existing benchmark, and no internal one, has run LeanDB against even one of these verticals. The restaurant and kernel prototypes are the only implemented domains, and neither has been scored against FinanceBench, LegalBench-RAG, or any comparable published set.

**A forward-looking idea worth recording here, not building now: LeanDB over its own domain — the codebase itself.** §4.3's code-search row (CodeSearchNet/CodeXGLUE/CoIR) and §4.6's turbopuffer aside are both about *unstructured* code search — embed a function, rank by similarity. A LeanDB base whose schema is parsed structure (declarations, call sites, types, module boundaries, the dependency graph) rather than embedded text would answer a different, typed class of question — "every caller of this function across the codebase," "every place a given type is constructed," "what changed in the public surface between two commits" — as an exact query rather than an approximate nearest-neighbor search. This is a genuinely different value proposition from CodeSearchNet-style semantic code search (typed structural queries vs. ranked semantic similarity), not a competitor to it, and no benchmark surveyed here — including the code-search entries in §4.3 — measures that kind of question at all. Recorded as a real, unscoped idea for later; nothing here treats it as built or evaluated.

**The honest summary.** "Will beat all benchmarks around search and retrieval, in all domains" is not a claim any single existing benchmark, or combination of them, can currently test — because the five traditions surveyed here measure five different things, most of which LeanDB does not attempt (large-scale unstructured ranking, raw engine throughput), and the one property most central to its thesis (a typed refusal instead of a confident wrong answer) has no published benchmark that scores it as a compiler-level guarantee rather than a probabilistic judgment call. That is not a weakness of the belief; it is the actual state of the external measurement landscape, and it is consistent with what this project's own whitepaper already says about itself.

## 8. Concrete next steps, ordered by how much they reuse existing, credible external data

1. **Adapt TrustSQL's methodology, not its dataset, as the first LeanDB-vs-SQL comparison.** Take BIRD's dev set (already public, already used as a difficulty reference by BIRD-CRITIC and BIRD-Interact) as the question source; run a plain `sqlite3`-driven agent arm and a LeanDB arm against the same questions; report execution accuracy and Silent-Wrong Rate side by side, using TrustSQL's penalty-based scoring as the reliability metric rather than inventing a new one. This reuses a credible, already-adversarial external dataset instead of an all-new corpus, addressing the design conversation's own worry that "a scoreboard you can't lose on convinces no one."
2. **Build a τ-bench-shaped task suite against one existing base** (tickets or eats), using the already-built `serve --http`/MCP surface and no new LeanDB infrastructure — score `pass^k`, database-state-diff correctness, and policy compliance the way τ-bench does, giving a second, independently-sourced reliability number that doesn't depend on TrustSQL's dataset or scoring choices.
3. **Only after both of those exist**, consider whether a genuinely new benchmark (the "Gauntlet," or something narrower) is needed to test the parts no existing benchmark reaches at all — the ingestion-time refusal (§5.2) and schema-evolution (§5.3) gaps — since those are the two structural absences this survey found that neither TrustSQL nor τ-bench covers.
